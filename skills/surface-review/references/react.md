# React + TypeScript pack

Sources: react.dev (thinking-in-react, passing-props-to-a-component, choosing-the-state-structure, sharing-state-between-components, reusing-logic-with-custom-hooks, passing-data-deeply-with-context, scaling-up-with-reducer-and-context, you-might-not-need-an-effect, manipulating-the-dom-with-refs, useImperativeHandle, reference/rules, learn/typescript) and legacy.reactjs.org/docs/composition-vs-inheritance (no react.dev successor; the only citation for the no-inheritance ruling). Consult them when a finding needs the verbatim rule. The docs do not cover compound components or discriminated-union props; those are community patterns, not citable idiom.

TypeScript is part of the surface here, not an add-on: the props and return types are the signatures the review measures. For prior art, the TanStack libraries (Query, Router, Table) are the ecosystem's benchmark: headless cores that own state and behaviour while the caller owns markup, single options-object entry points (`useQuery({ queryKey, queryFn })`), and status modelled as a discriminated union so that narrowing on `status === 'success'` proves `data` is present — illegal states unrepresentable at the type level. Weigh a surface under review against that bar as evidence, per the generic prior-art rules.

## Surface

For an exported component: its props type (names, types, defaults), which props are controlled versus initial-only, when its callback props fire, and what `children` accepts. For a custom hook: its arguments and return value, both reactive, plus the rules-of-hooks constraints every hook inherits (top level only, unconditionally). For a context module: the Provider component and consuming hooks. Behaviour over time is part of the contract: what re-renders, what resets when a prop changes, what an Effect does on unmount. Where a server/client boundary exists, whether the component carries `'use client'` and which of its props are serializable across that boundary is surface too.

## Contract expressions

- **Errors.** Mostly the platform's: a throw during render reaches an error boundary — but that channel has edges, since a failure in an event handler or async callback never does, and needs its own declared path (an error state in the union, an `onError` prop). For async status, one union (`'idle' | 'loading' | 'success' | 'error'`) instead of boolean pairs — the docs' "avoid contradictions in state" principle is shape test 4's state count.
- **Absence.** Optional props with destructuring defaults (`size = 100`). The caveat is contract: the default fires on missing or `undefined`, not on `null` or `0`.
- **Ownership and mutability.** Props are read-only snapshots; a component never mutates what it was passed, and asks the parent for different props instead. Every piece of state has exactly one owning component (the closest common parent of everything that renders from it); state that mirrors a prop desyncs and is a finding, unless the prop is genuinely initial-only, in which case its name says so: `initialColor`/`defaultColor` is the documented convention for "updates are ignored". State is minimal: not constant, not passed in, not computable from other state or props — "if you can compute it, it definitely isn't state". Data flows down: the parent owns fetched data and passes it; a child pushing data up from an Effect (`onFetched(data)`) inverts the flow and is a finding.
- **Lifetime and concurrency.** An Effect states its cleanup; hooks re-run every render, so hook arguments and returns are reactive values, and a custom hook shares stateful logic, never state itself — two callers get two independent states, and sharing means lifting. A hook's returned functions and objects are contract too: unstable identities across renders silently break consumers' dependency arrays, so returned functions are wrapped (`useCallback`) or declared unstable. Render is pure, and the surface must survive StrictMode's double-invoked render and effect setup/cleanup.
- **Sync and async.** Async work surfaces as a status union, not a promise handed out of render, and a hook that does I/O states its stale-response behaviour (the cleanup that ignores or aborts superseded requests) as contract. Parents are notified from the event handler that caused the change, in the same batch as the state update, never from an Effect.
- **Compatibility.** Props are the public surface: renaming a prop, changing when a callback fires, or moving a prop between controlled and initial-only breaks callers; a new optional prop with a default is the safe addition. Across a server/client boundary, adding `'use client'` or a required non-serializable prop (a function) breaks server callers.

## Idiom

- **Composition is the mechanism.** `children` is the hole a parent fills; specialization is a specific component rendering a generic one with props; passing JSX as props replaces threading data through layers ("if you forgot to extract some components along the way"). No component inheritance hierarchies, ever. Non-UI logic lives in plain modules, not components.
- **Component boundaries mirror the data model**; one concern per component; spread props "with restraint" — spreading everywhere means a missing `children` extraction.
- **State structure**: group state that updates together; a status union over contradictory booleans; compute during render instead of storing; store the selected ID, not a copy of the item; flatten deep nesting. To reset state when an identity prop changes, use `key`, not an Effect.
- **Custom hooks** are named `use` + capital only when they call hooks; a hook is extracted around a concrete high-level use case (`useChatRoom(options)`, `useMediaQuery(query)`) and "makes the calling code more declarative by constraining what it does". Lifecycle hooks (`useMount`, `useEffectOnce`) are a documented anti-pattern; a hook that adds nothing over the bare call it wraps is shallow, while one that packages state with its handling contract (`useFormInput` returning `{value, onChange}`) clears the depth test.
- **Context** ships as a module exporting a Provider and consuming hooks (`TasksProvider`, `useTasks()`), never a raw context object; a no-default context is created as `| null` with a consuming hook that throws outside the Provider.
- **Refs are the escape hatch**: only for imperative behaviour that cannot be a prop (focus, scroll, text selection, animation triggers); `useImperativeHandle` narrows the handle to named methods. `<Modal isOpen={isOpen} />`, not `modalRef.current.open()`.
- **Typing**: props are a named object type once they grow past a field or two; `ReactNode` for children; explicit union annotations where inference would widen (`useState<Status>('idle')`). Encode prop invariants structurally: a discriminated union when prop combinations are only legal together (react.dev shows the pattern for reducer actions; TanStack Query's narrowing return is the prior art for hook results), so the illegal combination fails to compile instead of needing a doc comment.

## Rulings

- **Props, then composition, then context.** The docs' explicit order for deep data: plain props first ("the person maintaining your code will be glad you've made the data flow explicit"), then extract components and pass children, then context for genuinely tree-wide data (theme, current user, routing). Context proposed where the first two serve is a finding under shape test 8.
- **Uncontrolled by default, controlled when coordination is real.** The docs state the trade-off without picking a side — uncontrolled "requires less configuration", controlled is "maximally flexible" at the cost of full parent configuration — so the default is this pack's verdict. A component that needs both offers the controlled pair (`value` + `onValueChange`) and the initial-only prop as distinct shapes, not one prop with both meanings — that is the two-owners braid.
- **Declarative over imperative.** A capability expressible as a prop is a prop; an imperative handle is reviewed as the escape hatch it is.
- **Extraction is not free depth.** A custom hook or child component earns its place by the depth test like any abstraction; splitting a component or wrapping a hook to shorten a file adds surface without adding function.

## Reflexes

- You will propose context for any prop passed two levels. Walk the props-then-composition order first.
- You will extract a custom hook for everything, including wrappers that add no capability over the hook they call. Run the depth test on the hook's own surface.
- You will propose an Effect to synchronize two pieces of state. The remedy is lifting, computing during render, or a `key` reset; "whenever you try to keep two different state variables synchronized, try lifting state up instead".
- You will reach for older idiom (render props, higher-order components, `forwardRef` ceremony) where current docs use plain props, hooks, and ref-as-prop.
- You will demand `memo` and `useCallback` on every callback prop a consumer passes. The citable obligation is the hook author's stable returns, not ceremony at every call site.
